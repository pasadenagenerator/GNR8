# GNR8 Evidence Package Implementation Contract (AAF-2)

## Purpose

This contract defines immutable evidence package storage and package-type requirements for the MVP Audit, Approval, and Evidence foundation. It is documentation only and does not create schemas, migrations, services, APIs, object storage, or runtime behavior.

## Evidence Truth Decision

Evidence packages must be immutable snapshots or immutable append-only ref sets. They may reference existing migration, runtime, domain, billing, provider, content, external workflow, and AI records, but a package must capture source watermarks and hashes so that an approval cannot silently point at changed evidence later.

Canonical package metadata, hashes, source watermarks, freshness labels, redaction labels, and retention classes live in Supabase/Postgres. Heavy artifacts may live in object storage with immutable refs and hashes stored in the control plane.

## Freshness Rules

Freshness must be evaluated against current source watermarks before approval and again immediately before action execution. A package that was fresh at approval time may be stale at execution time.

## Redaction Rules

Evidence builders should label sensitive items before display. Derived surfaces may show redacted package summaries while preserving original immutable package hashes and refs for authorized review.

## Failure Behavior

Missing source refs, missing hash, mutable object refs, stale freshness checks, redaction policy conflicts, or failed audit links make an evidence package invalid for privileged gates. Invalid evidence must create an Ops Inbox blocker and must not be auto-repaired by mutating the package in place.
