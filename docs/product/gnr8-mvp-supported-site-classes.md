# GNR8 MVP Supported Site Classes

MVP-1 canonical site-class boundary for the first approximately 200-site operator-assisted migration wave.

Allowed MVP statuses:

- supported
- supported with manual review
- import-only
- deferred
- out of scope

## Classification Matrix

| Site class | MVP status | Reason | Required evidence before migration | Required operator review | Launch/publish risk | Recovery expectation | Include in 200-site MVP wave |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Simple static brochure sites | supported | Best fit for static/raw-template import, runtime artifacts, preview, content slots, publish, and rollback. | Source URL, ownership/client mapping, page count estimate, public accessibility, basic asset availability. | Standard visual/content review and preview smoke. | Low: mainly missing assets, route mismatch, or visual drift. | Runtime rollback to prior version and content override rollback. | Yes; prioritize first. |
| Mostly static multi-page business websites | supported | Multi-page discovery/import foundations support route maps for static public pages. | Source URL, sitemap/route estimate, critical page list, redirects if known, public accessibility. | Route coverage review, visual/content review, preview smoke, link/navigation review. | Medium: missed pages, incorrect canonical routes, asset drift, redirects. | Runtime rollback plus route-map correction and re-import/replay. | Yes, with route limits and coverage threshold. |
| Small service business websites | supported | Usually static service/location/contact pages with manageable content corrections. | Source URL, contact CTA list, forms/widgets inventory, critical service pages. | Content accuracy, CTA/contact review, form/widget classification. | Low/Medium: incorrect contact path, form behavior, local SEO details. | Runtime rollback; content override rollback; DNS rollback if contact path breaks after domain launch. | Yes. |
| Public marketing sites with forms | supported with manual review | Static page migration is plausible; form behavior needs endpoint verification or approved replacement. | Form inventory, endpoint/action behavior, spam/compliance expectations, test submission evidence or replacement plan. | Technical form review, content review, client/account acceptance of any replacement. | High: lost leads, broken submissions, privacy/compliance exposure. | Rollback public runtime or restore original DNS/source form; content rollback for form copy. | Yes only after form behavior is verified or intentionally externalized. |
| Public websites with embedded widgets | supported with manual review | Static shell can migrate; widgets may depend on third-party scripts, embeds, or origins. | Widget inventory, provider URLs, criticality classification, source behavior screenshot/capture. | Technical widget review and client acceptance for replacements/fallbacks. | Medium/High: embeds break, block rendering, or fail on new domain. | Runtime rollback or approved static/external replacement; DNS rollback if widget is business-critical. | Yes when widgets are non-critical or verified. |
| WordPress sites | supported with manual review | MVP migrates the public static surface, not WordPress backend, plugins, users, admin, or editorial workflow. | Public URL, sitemap, plugin/form/widget inventory, blog/archive scope, admin/auth exclusions. | Stack review, form/plugin review, route/archive review, client acceptance of static-output boundary. | Medium/High: plugins, shortcodes, forms, dynamic archives, redirects, SEO. | GNR8 runtime rollback; original WordPress remains external recovery source until cutover is complete. | Yes for static public surface; no WP backend migration. |
| Webflow/Wix/Squarespace sites | supported with manual review | Public pages may be mostly static but platform scripts/forms/CMS features vary and no platform-specific adapter is MVP. | Source URL, route/page list, forms/CMS/widget inventory, custom code/script inventory. | Technical capture/script review, content/visual review, form/widget verification. | High for script-heavy pages, hosted forms, platform CMS, animations, or redirects. | Runtime rollback and possible DNS rollback to original platform. | Yes cautiously after prequalification; otherwise import-only. |
| Multilingual sites | supported with manual review | Static language routes can migrate; language switchers, hreflang, canonical URLs, and redirects require review. | Language list, route structure, critical localized pages, hreflang/canonical/redirect requirements. | Language route coverage, navigation/switcher review, SEO/redirect review. | Medium/High: missed locales, wrong canonicals, broken language navigation. | Runtime rollback; route/redirect correction and re-import; DNS rollback for severe launch issue. | Yes for simple static multilingual sites. |
| Blogs/news sites | supported with manual review | Static article archives can migrate; ongoing editorial CMS is not MVP. | Article/archive count, pagination, category/tag needs, RSS/search requirements, editorial update expectations. | Route/archive coverage, SEO review, client acceptance of static/editorial boundary. | Medium: incomplete archives, pagination/search, RSS, future publishing expectations. | Runtime rollback; archive route re-import; keep original CMS as fallback until accepted. | Yes for small/static archives; large active publications are deferred. |
| Public sites with heavy JavaScript | import-only | Rendered capture may produce evidence, but static runtime may not preserve app-like hydration, state, API calls, or interactive flows. | Script inventory, critical interaction list, rendered capture result, API dependency review. | Deep technical review and superadmin exception for any launch consideration. | High/Critical: blank pages, broken interactions, API/CORS/domain failures. | No normal publish; keep original as recovery. If exceptionally launched, runtime and DNS rollback required. | Usually no; include only as import-only triage. |
| Sites with third-party booking/reservation systems | supported with manual review | Public pages can migrate if booking remains external and is verified end-to-end. | Booking provider, embed/link behavior, callback/domain requirements, test booking evidence. | Technical booking-flow test and client/account review. | High: lost appointments, broken callbacks, revenue/client trust impact. | DNS/runtime rollback or restoration of original booking link/embed. | Yes only if booking flow remains external and passes testing. |
| Ecommerce sites | out of scope | Cart, checkout, inventory, taxes, orders, accounts, and payments exceed static migration and MVP billing boundaries. | Commerce platform identification for exclusion; public marketing pages may be separately scoped. | Superadmin out-of-scope confirmation. | Critical: revenue loss, payment/security/compliance failures. | Keep original commerce platform; DNS rollback required if accidental cutover. | No, except public non-commerce pages as import-only. |
| Member/authenticated sites | out of scope | Auth, sessions, accounts, private data, and permissions are not MVP migration capabilities. | Public/private boundary, auth dependency evidence, member functionality list. | Superadmin out-of-scope review. | Critical: data exposure, broken access, account loss. | Keep original platform; no GNR8 launch. | No. |
| Custom backend applications | out of scope | Static runtime does not migrate server-side business logic, databases, APIs, admin panels, or workflows. | Backend dependency inventory and public/static separability. | Technical out-of-scope review. | Critical: broken application behavior or data workflows. | Keep source application; no GNR8 launch except separable static marketing pages. | No. |
| Payment flows | out of scope | Payment handling is a compliance/revenue flow; GNR8 MVP cost/billing foundations are not customer payment migration. | Payment provider/flow identification and exclusion evidence. | Superadmin/account review. | Critical: revenue, chargeback, security, compliance. | Keep original/external payment flow; rollback DNS if affected. | No. |
| Compliance-heavy sites | deferred | Legal, healthcare, financial, regulated, accessibility, retention, and approval workflows need explicit policy outside MVP. | Compliance domain, required approvals, retention/audit requirements, risk owner. | Legal/compliance owner plus superadmin review. | Critical: regulatory or contractual breach. | Separate compliance runbook and legal signoff; otherwise no launch. | No for normal MVP wave; possible separate exception only. |
| Websites with complex SEO migration requirements | supported with manual review | Static migration can work, but redirect/canonical/metadata/history requirements are launch-critical. | Redirect map, canonical URL list, high-value pages, metadata requirements, analytics/search console baseline when available. | SEO/technical review, redirect smoke, client/account acceptance. | High: traffic loss, crawl/indexing issues, broken backlinks. | DNS/runtime rollback; redirect-map correction and re-publish only after approval. | Yes only with redirect runbook and accepted threshold. |
| Websites with unknown/damaged source state | import-only | Unknown ownership, broken source, malware, missing assets, damaged HTML, or unstable hosts cannot be launch-assumed. | Ownership proof, source availability, damage/security notes, capture diagnostics. | Intake review, security/source review, superadmin exception for continuation. | High/Critical depending on damage; evidence may be incomplete. | No publish until source is repaired/accepted; original/source recovery plan required. | Usually no; use for triage backlog only. |

## Launch Rules

| Rule | MVP requirement |
| --- | --- |
| Static-first | Launch is allowed only when the public experience can be served by static/raw-template/runtime artifacts plus approved published overrides. |
| Public-only | Authenticated, private, commerce, payment, and custom backend functionality remain outside the MVP launch boundary. |
| Manual review for risk | Forms, widgets, external scripts, platform builders, multilingual routes, blogs, booking flows, and complex SEO require operator review. |
| Import-only means no launch | Import-only sites can be captured for triage/review but must not enter publish-ready without a separate exception and architecture review. |
| Domain cutover | Custom domain publish requires Vercel/manual DNS readiness or an audited exception. |
| Recovery | Every launched site needs a known-good runtime rollback target or documented DNS/source recovery plan. |
| 200-site wave inclusion | The first wave should bias toward supported and manually reviewable sites; out-of-scope classes should be excluded from throughput commitments. |
